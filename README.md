# TripMind

TripMind is a Spring Boot travel planning project that turns a chat-style trip request into a structured travel plan. Instead of only giving generic suggestions, it tries to check feasibility first and then build a usable plan with budget context, flight and hotel estimates, weather guidance, advisor notes, and a day-by-day itinerary.

## Features

- Chat-based trip planning instead of a fixed form
- Separation between exploratory travel chat and actual planning mode
- Clarification of missing or ambiguous inputs like dates, trip type, and budget scope
- Budget verdict with estimated category-wise breakdown
- Flight and hotel planning with booking handoff links
- Weather context, packing guidance, and advisor notes
- Day-by-day itinerary generation
- Fallback handling when live or provider data is weak
- Bounded parallel agent execution with timeouts and graceful degradation
- Portable JSON plan persistence and indexed session history
- Spring AI structured trip extraction with Java validation and parser fallback
- Plan assistant with model tool calling, retrieved evidence, and visible tool execution
- Recalculated budget-stay and shorter-stay scenarios with an Apply action

## Tech Stack

- Java 21
- Spring Boot
- Spring MVC
- Spring Data JPA
- H2 database
- Redis Streams for workflow traces and agent events
- External provider integrations for places and weather
- Spring AI 2.0.1 (optional OpenAI-compatible chat model)
- Lexical RAG over curated planning guidance and linked Goa/Jaipur tourism summaries

## Explainable AI planning

After generating a plan, use **TripMind plan assistant** below the plan cards. Ask
"How can I reduce this trip's cost?" or "What historical places suit this Goa trip?"
The assistant receives the saved trip context and retrieved passages. Its tools can
inspect the saved plan, retrieve guidance, and calculate revision scenarios with the
same Java pricing engine used by the planner. It cannot book travel or invent live quotes.

Each scenario shows its planning total (including contingency), estimated savings,
budget verdict, and tradeoff. **Apply this revision** creates a new plan, preserving
the original plan, traveler needs, group size and budget. Session-linked plans keep
their session history. Explicit luxury preferences are not silently relaxed.

The evidence panel shows actual tool executions and retrieved source summaries.
Initial calculations/retrieval run in Java; an enabled model can request additional
tool calls. Offline mode displays a calculated comparison, clearly labeled as AI
unavailable. It does not pretend to answer arbitrary travel questions.

### Enable Spring AI

Existing `TRIPMIND_AI_PROVIDER` controls the earlier text-enrichment layer. The new
Spring AI integration has separate settings and defaults to disabled. For Groq,
add these to your local `.env` (use your own key, never commit it):

```dotenv
TRIPMIND_SPRING_AI_MODEL=openai
TRIPMIND_SPRING_AI_BASE_URL=https://api.groq.com/openai/v1
TRIPMIND_SPRING_AI_CHAT_MODEL=qwen/qwen3.8-27b
TRIPMIND_SPRING_AI_API_KEY=your_groq_key
```

`openai` here selects Spring AI's OpenAI-compatible client. The configured provider
must support chat completions and tool calling. Restart the app after changing these
settings. The key stays on the backend. An invalid/unavailable provider falls back
to calculated comparisons and the existing chat parser.

Structured extraction supplements missing trip fields; it does not overwrite
confirmed fields or bypass budget/date validation. Users still confirm the trip
details before planning. Current replanning offers two validated scenarios; free-form
edits to individual itinerary days are not yet implemented.

### Retrieval scope

The small corpus is `src/main/resources/knowledge/planning-guidance.tsv`.
Retrieval uses keyword overlap, not embeddings or a vector database. The corpus
includes internal planning policies and short, attributed official tourism summaries
for Goa and Jaipur checked on 2026-10-10. These are snapshots, not live opening hours,
ticket prices, availability or forecasts. Other destinations use existing place
providers and saved plan context. Expand the reviewed corpus before claiming broad
destination coverage.

### New API endpoints

- `POST /api/v1/trips/{requestId}/copilot` with `{"message":"Compare cheaper options"}`
- `POST /api/v1/trips/{requestId}/scenarios/{scenarioId}/apply`

The copilot response includes `mode`, `answer`, `evidence`, `toolsUsed` and `scenarios`.
Scenario IDs are generated by the server (`budget_stay`, `shorter_stay`); Apply
recomputes and validates the scenario instead of trusting client-supplied prices.

### Mentor demonstration

1. Create a round-trip Mumbai-to-Goa plan with explicit dates, travelers and total budget.
2. Ask the plan assistant to compare cheaper options; explain the largest cost category.
3. Show recalculated savings, the tool execution list and retrieved evidence.
4. Apply the shorter-stay revision; verify the dates and preserved traveler needs.
5. Ask about historical places and open a retrieved official tourism source.
6. Disable Spring AI and repeat the comparison to demonstrate graceful degradation.

## Project Layout

- `src/main/java` - application, controller, service, workflow, and agent logic
- `src/main/resources/static/index.html` - frontend UI
- `src/main/resources/application.properties` - base app configuration
- `src/main/resources/application-docker.properties` - Docker runtime overrides
- `.env.example` - example environment variables
- `Dockerfile` - container image build
- `docker-compose.yml` - local app + Redis setup

## Local Setup

### Prerequisites

- Java 21
- Maven wrapper included in the repo

### Run the app

1. Copy environment variables:

```bash
cp .env.example .env
```

2. Start the app:

```bash
./mvnw spring-boot:run
```

3. Open:

- App: `http://127.0.0.1:8080`
- H2 console: `http://127.0.0.1:8080/h2-console`

## Run With Docker

### Prerequisites

- Docker
- Docker Compose

### Start the containers

1. Copy environment variables:

```bash
cp .env.example .env
```

2. Build and start:

```bash
docker compose up --build
```

3. Open:

- App: `http://127.0.0.1:8080`

This setup runs:

- `tripmind-app` on port `8082`
- `tripmind-redis` on port `6379`

Persistent data is stored in:

- `./docker-data/app`
- `./docker-data/redis`

## Testing

To run the test suite:

```bash
./mvnw test
```

Tests use an isolated in-memory H2 database and disable optional Redis/provider integrations, so they do not require local infrastructure or API keys. GitHub Actions runs `./mvnw verify` on every pull request and push to `main`.

## Reliability Design

- Flight, hotel, weather, advisor, and itinerary work runs on a bounded application executor instead of the JVM common pool.
- Agent and provider failures degrade to explicit estimate-led results rather than failing the entire plan.
- External HTTP calls use configurable connect and read timeouts.
- Redis workflow tracing is optional; planning continues when Redis is unavailable.
- Plans are stored as JSON rather than Java-native serialized objects, keeping persisted payloads portable and inspectable.
- Database indexes support request lookup, session history, recent-plan ordering, and feedback lookup.

## Deployment

The easiest public deployment path for this project is Render.

- The repo includes a `render.yaml` blueprint
- The app supports host-assigned ports through `PORT`
- The `render` profile disables Redis-only workflow enhancements so the public demo can run as a single web service

If you deploy on Render, set the required API keys in the dashboard before the first deploy.

## Current Limitations

- Flight and hotel values are planning estimates, not confirmed inventory
- Some itinerary quality depends on third-party place data quality
- Broad country-level destinations should be narrowed to a city for the best plans
- Advanced multi-city optimization is still limited

TripMind now offers a local Streamable HTTP MCP server with saved-plan inspection, calculated revision comparisons and source-attributed guidance tools. Start with `./mvnw spring-boot:run -Dspring-boot.run.profiles=mcp` and connect a compatible client to `http://127.0.0.1:8080/mcp`.
